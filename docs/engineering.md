## 1. 项目换个目录、给别人用，配置就全乱了？

### 出了什么问题

各种配置和路径写死在不同文件里：项目根带着本机盘符，host / 端口、外仓地址、别人家 `.env` 的路径混在一起。仓一挪位置、换一台电脑、或交给别人跑，不是找不到 `data/`，就是密钥对不上，再不然把不该进 git 的东西带进仓库。

### 当时的情况

开发初期图省事。入口脚本各写一份 HOST / PORT / 路径，后来又想「收进一份 yaml 就整齐了」，于是 `backend/conf/config.yaml` 里同时出现本机根路径、监听地址、anyurl2text 地址。抽取还委托给外仓时，甚至用 `ANYURL2TEXT_ENV` 去读**另一个仓**的 `.env`，把那边的键整份注进本进程。

### 为什么会这样

当时没打算公开。本机能跑就行，没把「换目录会不会坏」和「密钥会不会泄漏」当成约束。几类东西变化原因其实不同，却被当成同一种「配置」塞在一起：盘符随机器变，端口跟进程走，密钥跟人走，相对数据目录才是各环境相同的。

### 试过哪些办法

- 全塞进 `config.yaml`，入口不再各写一份端口。结果审查分不清哪行能提交、哪行绝不能提交；换电脑仍要改 yaml。
- 用环境变量指向外仓 `.env` 做兜底，省得本仓再配一遍密钥。结果本仓启动会去碰别人家的盘符和密钥，公开前必须拆掉。

### 最后怎么解决

按「为什么会变」拆开，只留四个落点：

- 项目根：`backend/conf/base.py` 用 `__file__` 推算，不写盘符。
- 本服务 host / port：写在 `backend/online/server.py` / `service/embed/server.py`。
- 相对数据目录、向量库目录：进仓的 `backend/conf/config.yaml`。权重目录是 `service/embed/models/`（下载脚本同目录），不进 yaml。
- 第三方地址和密钥：只读本仓 `.env`（模板 `.env_example` 进仓）。`backend.conf.apply_env()` 是唯一读取点。

抽取和外仓解耦之后，读外仓 `.env` 的兜底删掉。换目录不用改配置；密钥进不了仓。

## 2. 根路径已经集中过了，脚本为什么还要改搜索路径？

### 出了什么问题

项目根已经只在 `backend/conf/base.py` 推算，启动文件不要再算一遍。可是 `scripts/` 里的入库、评测一打开，仍常见几行「先把仓库根插进 `sys.path`，再 import backend.conf as conf」。看起来像每个脚本偷偷写了第二份 ROOT。

### 当时的情况

长驻服务从仓库根 `python -m` 起对应层包（当时是 `online.server` / `embed.server`），解释器把仓库根放进搜索路径，`import backend.conf as conf` 直接成功，`base.py` 再保证 ROOT 在路径里。脚本习惯写成 `python scripts/ingest/ingest.py`，从子目录启动。

### 为什么会这样

这是解释器怎么定位脚本，不是根常量写了两份。`python scripts/ingest/ingest.py` 时，`sys.path[0]` 是 `scripts/ingest/`，此时还 import 不到 `conf`，里面的 ROOT 用不上。盘符 ROOT 若再写进脚本，换目录又坏一次。

### 试过哪些办法

- 每个脚本自己写一份盘符路径当 ROOT。和 yaml 写死盘符是同一类错。
- 要求一律从仓库根 `python -m scripts.xxx`。本仓脚本不是包，也容易和「不要发明 CLI」拧着。

### 最后怎么解决

从仓库根 `python -m` 起的层包入口直接 `import backend.conf as conf`。`scripts/` 里只插仓库根以便找到配置包（场景子目录是上三级），不要在脚本里再赋盘符。插完立刻从 `backend/conf/base.py` 读 ROOT。层模块不要自己改搜索路径，假定入口已经做过。项目根仍然只有一处推算。

## 3. 测试已经中止了，机器为什么还在空转？

### 出了什么问题

2026-10-08，一轮被中止的 `pytest tests -q` 在后台空转一小时，烧掉约 3400 秒 CPU；同一条命令正常跑完只要约 21 秒。另一边，要写磁盘的用例用 pytest 自带的 `tmp_path`，在沙箱里建出来的目录权限是 `0o700`，连创建者都列不出，测试卡死或直接失败。

### 当时的情况

AI 会话里把入库、评测、全量 pytest 放在前台干等。中止对话只杀了外壳进程。Windows 沙箱对系统 Temp 和过严的目录权限不友好。

### 为什么会这样

中止只杀 shell，用该 shell 拉起的 Python 孙进程还活着。看不到进度的长任务看起来像卡死，于是再中止、再拉起，残留叠加。`tmp_path` 的权限假设在这套沙箱里不成立。

### 试过哪些办法

- 把前台等待时间加长。卡死时仍然看不到进度，残留进程问题没解决。
- 继续用系统 Temp 和 `tmp_path`。部分沙箱直接拒写。

### 最后怎么解决

长任务后台起、要停就停作业本身；前台等待不超过 120 秒。中止之后核对有没有留下 python 残留进程。pytest 在 `pyproject.toml` 的 `[tool.pytest.ini_options]` 里打开 `faulthandler_timeout`，到点自己退出。要写磁盘的用例走 `tests/conftest.py` 的 `work_dir`，不用 `tmp_path`。入库按 `EMBED_REQUEST_BATCH` 切批并打进度，避免整库一次 POST 把客户端读超时打满。
